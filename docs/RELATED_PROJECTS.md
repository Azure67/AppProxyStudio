# 同类项目与设计取舍

调研日期：2026-11-20。依据项目 README、文档与公开 issue。issue 是特定环境中的用户报告，不代表所有版本都存在该问题；下列改进建议是本项目的判断。

| 项目 | 可借鉴的优点 | 限制或风险 | 本项目的选择 |
| --- | --- | --- | --- |
| [ProxiFyre](https://github.com/wiresock/proxifyre) | 按应用有序匹配、多 SOCKS5 出口、排除规则、GUI 与服务分离；明确解释 DNS 与权限边界 | 官方文档列出额外驱动依赖、DNS 默认直连、部分 IPv6 分片直通及凭据明文保存 | 保持应用→通道映射可见；不自动把所有子进程加入；明确不是防泄漏工具。暂不引入额外驱动/服务 |
| [Clash Verge Rev](https://github.com/clash-verge-rev/clash-verge-rev) | 配置校验、可视化规则、服务/sidecar 模式、主题和配置备份 | 功能多意味着启动、更新和服务之间需要协调；公开 issue 有 TUN/ICS/其他适配器共存问题报告 | 保留先校验后应用、失败回滚和单任务操作；后续先做只读冲突诊断，不能擅自停其他 VPN |
| [v2rayN](https://github.com/2dust/v2rayN) | 多核心支持、平台/架构清晰、发布文件签名与文档入口 | 多核心能力不同，不能据界面选项推断所有核心都支持；更多核心会增加测试矩阵（本项目判断） | 当前只维护一个已测 Mihomo 基线；固定版本、下载校验、明确协议导入边界，再考虑多核心 |

## 重点问题与证据

1. **选了应用不等于实际连接已代理。** [ProxiFyre #187](https://github.com/wiresock/proxifyre/issues/187) 报告 AI 桌面应用在显式环境代理下可用、按应用分流不生效，原因尚不能仅凭报告确定。本项目保留辅助 EXE 关联与实际连接规则展示；不能把“代理开启”当作连通性测试结果。
2. **短命 UDP 需要专门验证。** [ProxiFyre #193](https://github.com/wiresock/proxifyre/issues/193) 报告快速关闭的 UDP socket 可能赶在进程归属解析前消失。不能把该实现的缺陷直接归因到 Mihomo，但它提醒本项目补测短命 UDP、QUIC、IPv6 和退出重连。当前 TCP/本地模拟节点测试不覆盖这些场景。
3. **TUN 共存不是一个开关就能保证。** [Clash Verge Rev #8199](https://github.com/clash-verge-rev/clash-verge-rev/issues/8199) 报告 Windows ICS 与其他客户端残留适配器的冲突。不能简单“删除网卡”修复；应先收集路由、DNS、接口与核心状态。
4. **启动超时不一定意味着服务缺失。** [Clash Verge Rev #8488](https://github.com/clash-verge-rev/clash-verge-rev/issues/8488) 是 macOS 冷启动/IPC/订阅更新竞争报告，不是 Windows 已确认问题。可借鉴的工程原则是将配置校验、核心就绪、服务存在分开判断，避免自动重装和并发更新。

## 已有措施与本次落地

- 已有：主/辅助路径冲突校验、自动关联限制路径范围、变更配置前核心校验、热更新失败回滚、控制 API 回环地址与随机令牌、退出回收核心。
- 已有：联网进程显示真实核心规则；引擎停用时明确标记“未核实”。
- 本次：公开源码与运行数据隔离；安装脚本固定核心下载并检查 SHA-256；测试去掉对真实用户配置的依赖；增加 Windows CI；明确当前尚未验证的兼容性。

## 后续优先级（尚未实现）

- P0：只读启动诊断，分别检测管理员权限、端口、已有 TUN、系统/环境显式代理；提供具体修复建议。
- P0：DNS、IPv6、QUIC、短命 UDP、断网恢复、进程升级后的路径变化测试矩阵。
- P1：可预览脱敏结果的诊断导出，默认不包含订阅、密码、token 和访问目标。
- P1：托盘与服务生命周期设计；用户明确开启后才后台驻留/开机启动。
- P2：订阅定时更新、配置备份与主题切换，更新串行化并保留可恢复版本。
